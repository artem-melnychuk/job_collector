# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Note: this file is the terse operational reference.

## Commands

Run everything from the repo root using the project venv (no system Python):

```powershell
# install deps
.venv\Scripts\python.exe -m pip install -r requirements.txt

# validate config only, no collectors started
.venv\Scripts\python.exe -B scripts\collector.py --dry-run

# collect from all sources (LinkedIn, Company Careers, Djinni, DOU, RemoteOK, We Work Remotely, Jobicy, Himalayas — WTTJ is excluded from "all", see below)
.venv\Scripts\python.exe -B scripts\collector.py --source all --limit 50

# collect from one source, headless
.venv\Scripts\python.exe -B scripts\collector.py --source company_careers --limit 50 --headless

# collect one exact configured query (must match config/job_queries.yaml)
.venv\Scripts\python.exe -B scripts\collector.py --source company_careers --query "Trading Analyst" --limit 20 --headless

# recheck saved URLs and update availability_status
.venv\Scripts\python.exe -B scripts\collector.py --check-availability --check-limit 500 --headless

# open browser for manual WTTJ login, saved into the persistent profile
.venv\Scripts\python.exe -B scripts\collector.py --login

# run the rule-based analyzer over the processed dataset
.venv\Scripts\python.exe -B scripts\analyzer.py

# print/save a skill-gap and rejection-reason report from manual_review + jobs_master
.venv\Scripts\python.exe -B scripts\skills_gap_report.py

# count how often tools and certifications appear in the collected postings (read-only, writes reports/)
.venv\Scripts\python.exe -B scripts\certification_analysis.py

# print/save the list of still-active near-fit postings worth applying to now
.venv\Scripts\python.exe -B scripts\active_near_fit_report.py

# recheck previously-rejected "board exists, 0 jobs" companies (Kraken, Prodly) for new postings
.venv\Scripts\python.exe -B scripts\recheck_rejected_boards.py

# mine a Notion-embed table (e.g. a curated company list) into a CSV via its "Load more" pagination
.venv\Scripts\python.exe -B scripts\mine_notion_companies.py --headless

# score undecided postings for candidate fit via an LLM call (costs money; needs $env:ANTHROPIC_API_KEY)
.venv\Scripts\python.exe -B scripts\fit_score.py --limit 20

# draft CV bullets + a short pitch for "Подходит" + active postings (costs money; needs $env:ANTHROPIC_API_KEY)
.venv\Scripts\python.exe -B scripts\cv_draft.py --limit 10

# review existing CV/drafts/*.md for honesty/relevance/tone via a separate LLM call (costs money; needs $env:ANTHROPIC_API_KEY)
.venv\Scripts\python.exe -B scripts\cv_review.py --limit 10

# assemble a cover-note PDF per draft + ATS keyword check (free, no API key needed)
.venv\Scripts\python.exe -B scripts\cv_pdf.py --limit 20

# sync the application workflow: turn "applied" marks into the applications log, refresh active_near_fit (free)
.venv\Scripts\python.exe -B scripts\applications_tracker.py

# run all tests
.venv\Scripts\python.exe -B -m unittest discover -s tests

# run one test module / class / method
.venv\Scripts\python.exe -B -m unittest tests.test_ids_and_deduplication
.venv\Scripts\python.exe -B -m unittest tests.test_ids_and_deduplication.JobIdentityTests.test_tracking_parameters_do_not_change_normalized_url
```

LinkedIn and WTTJ collection opens a real (or headless) Chromium via Playwright with a persistent profile at `.browser_profile/`; without `--headless` a visible browser window is expected. `--login` must be run once (or re-run when the session expires) before WTTJ collection works.

## Architecture

Pipeline: `SEARCH → COLLECT → DEDUPLICATE → SAVE RAW` per run, then merge into the accumulating processed dataset. A separate pass: `LOAD PROCESSED → CLASSIFY → EXTRACT SKILLS → SAVE PROCESSED` (the analyzer).

**`core/models.py`** — single `JobRecord` dataclass every collector returns. Nearly all fields are plain strings (sources give incomplete/inconsistent data; normalization happens later, not at parse time). `JOB_RECORD_COLUMNS` derived from the dataclass defines the canonical export column order. Field groups: identity (`job_id`, `source`, `url`), listing (`title`, `company`, `full_text`), geography (`city_region` as originally collected, plus `city`/`region` split out from it and `country`), terms (`work_format`, `source_work_format`, `contract_type`, `salary`, plus `salary_usd_equivalent`), provenance (`date_collected`, `date_published`, `search_query`, `note`), state (`status`, `availability_status`), analysis (`job_category`, `role_family`, `role_subcategory`, `seniority`, `years_experience_min/max`, `skills_all`, `required_skills`, `preferred_skills`, `analysis_note`, plus `fit_score`/`fit_reasoning`). `city`/`region`/`salary_usd_equivalent` are collector-empty — filled by the analyzer pass, not at parse time (see `core/analyzer.py`/`core/metadata.py` below). `fit_score`/`fit_reasoning` are collector- and analyzer-empty too — filled only by the explicitly-invoked, billed `scripts/fit_score.py` (see `core/fit_score.py` below). Dates (since 2026-10-05): `date_collected` means first seen — a re-collect keeps the earliest (`core/storage.py:_reconcile_updated`); `date_published` also keeps the earliest seen, since Djinni and LinkedIn move a posting's date forward when it is bumped or reposted. Greenhouse gives `first_published` (not `updated_at`, which moves on every edit), Lever `createdAt`, and LinkedIn's "2 days ago" is pinned to a date at collect time (`core/metadata.py:resolve_relative_date`); `core/metadata.py:parse_date` reads all of these formats. Existing rows were backfilled from `data/raw/` the same day.

**`core/config.py`** — loads the three YAML files under `config/` (`job_queries.yaml`, `companies.yaml`, `settings.yaml`) via `load_configuration()`. `select_queries()` flattens `job_queries.yaml` categories into a flat `[{query, category}]` list; `--query` filters to one exact match (case-insensitive).

**`collectors/base.py`** — `BaseCollector.collect(context, queries, limit) -> CollectorResult` is the contract every adapter implements (async, takes a shared Playwright `BrowserContext`). `setting()` reads nested settings dicts without a config class. All three adapters run inside one shared persistent browser context per `scripts/collector.py:collect_sources`.

Adapters, each in `collectors/`:
- **`linkedin.py`** — searches `/jobs/search/`, collects `/jobs/view/` links, parses JSON-LD `JobPosting` first with CSS-selector fallback. Detects `active`/`closed`/`unknown`. LinkedIn has no stable public API — authwalls and HTML drift are expected failure modes, not bugs to "fix".
- **`wttj.py`** — paginates a fixed topic page (`/fr/pages/emploi-data-analyst?query=...&page=N`), same JSON-LD-first parsing. **The topic page does not reliably honor the query filter** — treat WTTJ as reliable for Data Analyst but not for Crypto/Trading/Risk/Quant; `search_query` records intent, not proof of relevance. Location (`locality`/`region`/country) is merged into one `city_region` string; there is no separate `city` field yet. **Excluded from `--source all`** (`scripts/collector.py:collect_sources`) since 2026-09-04: this topic page is the only one reachable without a login, and it is a French-market page — sampling raw (pre-filter) results confirmed every posting is either French-language (correctly rejected by `requires_french`) or Hybrid (correctly rejected by `has_disallowed_work_format`). The exclusion filters aren't malfunctioning; this specific source can't produce a match for a remote-only, non-French-speaking profile. Still runnable explicitly via `--source wttj` if the profile requirements change or a better public entry point is found.
- **`company_careers.py`** — pulls Greenhouse (`boards-api.greenhouse.io/v1/boards/{slug}/jobs?content=true`) and Lever (`api.lever.co/v0/postings/{slug}?mode=json`) boards that are explicitly listed in `config/companies.yaml`. A "priority company" without a board entry there is silently not collected. Local text filtering by query phrase/significant words. Lever boards can set an optional `host` (e.g. Kaiko is EU-hosted at `api.eu.lever.co`, not the default `api.lever.co` — the default host 404s). A `slug` can point to a shared multi-brand board (Cumberland's crypto roles live on DRW's single Greenhouse board, slug `drweng`, alongside ~150 unrelated DRW postings) — the existing per-title query match still filters those correctly. BambooHR boards (`ats: "bamboohr"`, added 2026-10-05 for IWConnect) use the two public JSON endpoints behind the company's own careers page: `https://{slug}.bamboohr.com/careers/list` (titles, ids, locations, no description) and `/careers/{id}/detail` (full posting), so the detail is fetched only for titles that matched a query, and a failed detail costs only that posting. `locationType` "1" is Remote and "2" Hybrid (confirmed against the rendered pages); other values were not seen and fall back to text inference. Salary comes from the structured `compensation` field when it is filled, otherwise from text like Greenhouse/Lever.
- **`djinni.py`** — Ukraine's largest IT job board, added because remote-first EU/US roles keep hard-blocking on residency/visa while Ukraine-market roles don't. RSS-based (`djinni.co/jobs/rss/?primary_keyword=...`), no browser page rendering needed — same "plain HTTP GET" reliability as the Greenhouse/Lever adapters above, not the fragile Playwright-scraping path. Own query vocabulary in `job_queries.yaml`'s `djinni_categories` (Djinni's English UI category labels, e.g. `"Data Analytics"` — NOT the same phrases as the shared `categories` list), since postings are in Ukrainian/Russian and the shared English queries wouldn't match. **An unrecognized `primary_keyword` silently falls back to Djinni's unfiltered all-jobs feed instead of erroring** — same trap as WTTJ's topic page; only add a category value after manually confirming it filters at `https://djinni.co/jobs/?primary_keyword=<value>`. A value that once worked can stop working (`"Data Analytics"` did on 2026-09-29 and was removed); the collector now keeps only RSS items whose `<category>` equals the keyword and reports a feed with zero such items as an error, so a silent fallback no longer turns into noise records. Company name is a heuristic (first `<strong>` tag in the description HTML), not a structured field. Not in `CONTEXT_FILTERED_SOURCES` — Djinni's `primary_keyword` filter is itself the relevance check, and title text is Ukrainian/Russian so the English `query_matches` title check would wrongly reject legitimate results.
- **`dou.py`** — DOU.ua (Ukraine's main IT community board), added 2026-10-05. Plain HTTP GET + RSS (`jobs.dou.ua/vacancies/feeds/?category=…` / `?search=…`, 25 newest per feed, full description included, no bot challenge), same tier as `djinni.py`. Feeds come from `settings.yaml` `sources.dou` (category Analyst + four search phrases). The `<title>` is structured — `<Title> в <Company>[, $min–max][, places]` — so company, a monthly salary (stored as `$X–Y/month`, never guessed from text) and places come from it; a company name can contain a comma (e.g. "Delta Labs, Studio 3"), so `parse_title` extends the company until the first salary or place token. Places drive `work_format` ("віддалено" → Remote, office cities only → On-site, so `disallowed_onsite_countries` drops office-only Ukraine postings) and `country` (Ukrainian city/"Україна" → Ukraine, "Місто (Країна)" → mapped country). Search is full-text, so titles must still name an analyst role (EN/UK/RU regex); like Djinni it is not in `CONTEXT_FILTERED_SOURCES`, and the English `query_matches` only labels `search_query`. Many Ukrainian companies cross-post to Djinni; `country="Ukraine"` plus "віддалено"/"кордоном" as region words in `core/cross_dedup.py` let those copies group. Availability: a removed posting returns 404 (generic detector); how DOU marks a closed-but-not-removed posting was not observed yet.
- **`remoteok.py`** — remote-only tech job board, added because it's remote-by-construction (no work-format guessing needed — `work_format` is hardcoded `"Remote"`). Plain HTTP GET against `remoteok.com/api`, JSON, no browser rendering. **The documented `?tag=` query parameter does NOT filter server-side** — passing it returns zero postings (verified 2026-09-06), so the collector fetches the unfiltered feed and applies the same local `query_matches` title check as `company_careers.py` before keeping a record. Not in `CONTEXT_FILTERED_SOURCES` for that reason. **The unfiltered feed is only the ~100 most-recently-posted jobs platform-wide**, not a paginated archive — expect a handful of analyst/data-titled matches per run (spot-checked: 2-4 per 100), accumulating across repeated runs as the feed rotates, not a bulk one-time yield.
- **`weworkremotely.py`** — remote-only job board, added 2026-09-09. Plain HTTP GET + RSS at `weworkremotely.com/remote-jobs.rss`, same reliability tier as `djinni.py`/`remoteok.py`. **The site's old per-category RSS URLs (`/categories/remote-...-jobs.rss`) no longer work** (301-redirect to the homepage, presumably a site redesign) — only the single unfiltered feed is live, with no "Data"/"Analytics" category of its own, so — like `remoteok.py` — this collector filters locally by title via `query_matches` and is not in `CONTEXT_FILTERED_SOURCES`. Better-structured than Djinni/RemoteOK's feeds though: `<region>`/`<country>`/`<state>` are separate fields, and the title itself is `"{Company}: {Job Title}"` — a clean split, not an HTML heuristic. Same small-window caveat as RemoteOK: only ~90-100 most-recent postings platform-wide, skewed toward eng/sales/management roles — a spot-check found zero analyst-titled matches among 90 items, so expect sporadic, accumulating-over-time yield, not a reliable per-run one. Investigated CryptoJobsList and Web3.career as crypto-domain-specific alternatives (matching the candidate's actual crypto/NFT background) — **neither has a usable feed**: CryptoJobsList's advertised RSS (`api.cryptojobslist.com/jobs.rss`) returns valid XML with zero `<item>` entries despite the site itself having active listings (confirmed 2026-09-09), and Web3.career advertises no RSS/feed at all. Both would need full HTML-scraping (LinkedIn/WTTJ-tier fragility) to add — not pursued, same reasoning as the work_ua/robota_ua sunk-cost note above; revisit only if the user explicitly wants it.
- **`jobicy.py`** / **`himalayas.py`** — remote job boards with public JSON APIs, added 2026-09-30 (plain HTTP GET, same tier as `remoteok.py`). Both filter by eligibility server-side, which is what makes them worth having: Jobicy `geo=france` returns only postings open to applicants in France (Europe/EMEA/Anywhere or lists naming France; without it 27 of 50 "data analyst" results were USA-only), Himalayas `country=France` returns France-eligible plus worldwide postings. Their keyword search is broad or loose (Himalayas "data analyst" also returns "Behavior Analyst"), so each sends a few broad terms from `settings.yaml` `sources.jobicy`/`sources.himalayas` (default "analyst", "analytics") and keeps titles matching `job_queries.yaml` via `query_matches`, like `remoteok.py` — 2 requests for Jobicy, up to 2×5 pages of 20 for Himalayas, not one per query. Etiquette: Jobicy asks for no polling more often than hourly and credit plus the original job URL; Himalayas is rate limited (429), refreshes data daily, and asks for a link back — both records keep the source URL and name the source in `note`. Salary comes from structured fields only; the text fallback `remoteok.py` uses produced fake salaries ("10 EUR" meal allowance) on the first live run. The same guess also ran later, in `--check-availability`'s pre-check metadata backfill, and put the fake figures back the next day; `scripts/collector.py:backfill_saved_metadata` now skips `STRUCTURED_SALARY_SOURCES`. First run: Jobicy 3 new, Himalayas 8 new. **Indeed was checked the same day and is not addable:** its RSS returns 404 and its search page answers 403 with a Cloudflare captcha — same class as `work_ua`/`robota_ua`, don't try to work around it.
- **`work_ua.py`** / **`robota_ua.py`** — Ukraine's two largest *general* (not IT-only) job boards, added 2026-09-07 alongside Djinni because analyst roles at Ukrainian banks/retail/fintech (which value Excel/reporting over deep coding) show up here, not on IT-only boards — same rationale as Djinni: a native Ukrainian/Russian speaker has a real edge on this market regardless of physical location. Own query vocabulary in `job_queries.yaml`'s `ukrainian_categories` (free-text Ukrainian phrases, unlike Djinni's English category-filter labels). Neither has a public search API/RSS, so both are Playwright-rendered HTML (`page.goto`, not `get_with_retry`) with CSS-selector scraping, same fragility as `linkedin.py`/`wttj.py` — worse, in fact: **both are currently blocked by Cloudflare-style anti-bot challenges and are NOT in `--source all`.** `robota.ua` blocks consistently in both headless and non-headless mode, even with a fresh browser profile. `work.ua` is harder to reason about, not easier: one non-headless attempt succeeded, an identical repeat minutes later (same profile) was blocked — the profile/IP seems to get flagged after a handful of requests regardless of the headless flag. `is_challenge_page_title()` in each module turns a block into a visible error instead of a silent "0 results", but neither source is dependable today. Still selectable via `--source work_ua` / `--source robota_ua` for anyone who wants to retry (different IP, proxy, cooldown period, etc.) — kept rather than deleted since the scraping logic itself (selectors, pagination, salary/work-format parsing) is verified correct against real pages, only the anti-bot layer blocks it. **Sunk-cost trap, flagged 2026-09-08: don't spend further session time trying to fix the anti-bot blocking itself** (proxies, fingerprint tuning, header/UA tricks, etc.) — the 2026-09-07 stealth-context experiment already showed why this doesn't pay off: it bought exactly 3 clean requests before the same profile got flagged again, so each retry burns effort for a result that doesn't hold. Only revisit if the user explicitly asks, or an external condition changes (a proxy/IP the user already has, a long unattended cooldown, or the sites' own protection breaking, as already observed happening to robota.ua independent of anything this repo does).

**`core/ids.py` / `core/deduplication.py`** — identity is `source + normalized(url)` (tracking params and trailing slash stripped), falling back to `source + company + title + city_region` when there's no URL. `job_id = {source_slug}_{sha1[:12]}`. This makes reruns idempotent. That identity is per source, so the same job under a different URL (another board, or a repost) is a separate row.

**`core/cross_dedup.py`** (added 2026-10-02, run by `scripts/analyzer.py` after the per-record pass) — labels such copies with a shared `duplicate_group` (the group's smallest `job_id`; blank for unique postings). Nothing is merged or deleted: every copy keeps its own row, `manual_review` decision and availability. Match = company equal after normalization (legal suffixes, "(Parent)", CamelCase) or difflib ratio >= 0.92, title equal or ratio >= 0.93, and compatible locations: two named places must share a token (a plain company+title key would merge Coinbase's same role in "Remote - USA" and "Hyderabad, India"), region words (Remote/Worldwide/Europe/EMEA…) match anything, and a blank location does not match a named one (blank = unknown; a wrong merge hides a real job, a missed one only shows a duplicate row). Greedy clustering requires a match with every member, so a vague posting cannot chain two incompatible ones. On 199 rows: 5 groups / 10 rows, 1 group across sources (Canonical on Jobicy + Himalayas). `active_near_fit` shows one row per group (preferring the company's own ATS, see `SOURCE_PREFERENCE`) with the other copies' sources in `also_on`, and applying to any copy takes the whole group off the list. Since 2026-10-05 an ungraded copy also inherits the grade of a graded one (`inherit_group_decisions`, called in `core/storage.py:_manual_review_dataframe` on every save): `decision`, `main_reason` and the other input columns except `applied` and `review_notes`, plus a note naming the donor copy; graded copies that disagree are left for a human. Analysis/report dedup (`core/skill_recommendations.py:dedupe_rows`, `certification_analysis.py`) still uses its own looser company+title key.

**`core/storage.py`** — `load_records`/`save_records`/`merge_records`. Raw XLSX (one per run, timestamped in `data/raw/`) has a single `raw_jobs` sheet plus CSV (UTF-8 with BOM). Processed XLSX (`data/processed/crypto_jobs_clean_v1.xlsx`, accumulative) has `jobs_master` (full canonical table; hidden in Excel but the one sheet every script reads records from) and `manual_review`, plus the sheets other scripts add (`active_near_fit`, `applications`, `skills_gap`, `skill_recommendations`). `jobs_view`/`jobs_text` (read-only column subsets nothing consumed) were dropped 2026-09-30; `save_records` deletes leftover copies. `manual_review` (hand-filled fit assessment, keyed by `job_id` and preserved across reruns). Merge classifies each record as `new`/`existing`/`updated`.

**`core/analyzer.py`** (driven by `scripts/analyzer.py`) — rule-based, no ML/LLM. Infers `role_family`/`role_subcategory`, estimates `seniority` from title/text heuristics, extracts normalized `skills_all`, and splits `required_skills`/`preferred_skills` using known marker phrases. Everything it writes is explicitly preliminary (`analysis_note`) — title-based seniority guesses are known to be unreliable, and skills regex has false positives on short tokens (`R`) and generic terms (`ML`, `crypto`, `market data`).

**`core/metadata.py`** — salary/country/work-format extraction helpers shared across collectors and the availability checker.

**`scripts/active_near_fit_report.py`** — same manual_review + jobs_master join shape as skills_gap_report.py, but simpler: filters to postings that are both near-fit (`Подходит`/`Возможно`, not filtered) and still `active` per the last `--check-availability` run, and writes an `active_near_fit` sheet (decision-colored rows, same green/yellow convention as `manual_review`) as a ready-to-work applications list. Point-in-time — re-run after `--check-availability` to refresh, doesn't check liveness itself.

**`core/skills_gap.py`** (driven by `scripts/skills_gap_report.py`) — joins `jobs_master` (analyzer output: `required_skills`/`preferred_skills`) with `manual_review` (`decision`, `should_be_filtered`, `main_reason`, `review_notes`) by `job_id` to answer "what's costing me otherwise-plausible roles": which skills recur in near-fit (`Подходит`/`Возможно`) postings but aren't in the candidate's known toolset (`KNOWN_SKILLS`, sourced from `CV/resume_improved.html`'s own Skills section — update by hand if the resume changes), and which rejection-reason bucket (keyword-matched against `main_reason`+`review_notes`) accounts for the most `Не подходит`/`should_be_filtered=Да` postings. Buckets are split into learnable (coding depth, domain expertise, seniority, experience years — worth studying) vs structural (language, location/on-site, low-quality listing — not fixable by studying). Writes a `skills_gap` sheet into the processed workbook alongside printing to console.

**`core/skill_recommendations.py`** (also driven by `scripts/skills_gap_report.py`, added 2026-09-25) — turns the skill-gap counts into study recommendations backed by market data. For every missing or partially known skill it adds what share of ALL collected postings (deduped by normalized company+title, not only the hand-picked near-fit ones) mention the skill, using the analyzer's own `SKILL_RULES` patterns, and how many postings put a certification word within 60 characters of it. The action is computed from thresholds, never from a hardcoded tool name: `learn` (>=10% of the market and >=2 near-fit postings), `optional` (>=3%), `low priority`; skills in `LOW_CONFIDENCE_SKILLS` (`R`, `Machine Learning`, whose patterns match short or generic tokens) are downgraded to `verify first`. A certificate is called `worth considering` only if >=3 postings mention one, otherwise the advice is to learn the skill and skip the exam. Prints a "What to study" section and writes a `skill_recommendations` sheet (rows with action `learn` green). Known limit: interchangeable tools (Power BI / Tableau / Looker) are rated independently, so several can read `learn` even though learning one covers most of the demand. The market counts are mentions anywhere in the posting, a looser definition than the analyzer's required/preferred split, so they read higher than the near-fit counts by design.

**`scripts/certification_analysis.py`** — the market-side counterpart to `skills_gap`: counts, per posting (one mention per term, postings duplicated by normalized company+title collapsed first), how many collected postings mention each tool (SQL, Python, Excel, Power BI, Tableau, Looker, GA4, dbt, BigQuery, Snowflake, Dune, Metabase) and each certification (PL-300, Tableau, Google/IBM, GA4, CompTIA Data+, GitHub Foundations, dbt, plus a generic "certification near a tool name"), split by seniority and location (remote / Europe / other). Certificate rows also get required / preferred / merely-mentioned, decided by the nearest marker within +-150 characters. Term patterns live in `TOOLS`/`CERTIFICATES`; two are deliberately non-obvious — bare "Excel" is skipped when it is the English verb ("excel in", "to excel"), and bare "Dune" only counts capitalized. Read-only over `jobs_master`; writes `reports/certifications.csv` and `reports/certifications.md` (top-10 terms, certificate table, 3 random quotes per term to eyeball false positives). `reports/` is gitignored because it is derived from the real dataset and regenerable. Refuses to run (asks instead of guessing) if required columns are missing or fewer than 50 postings remain after dedup. The script only reports demand; study recommendations built from it (certificates, tools to learn) are personal and live outside the code.

**`scripts/recheck_rejected_boards.py`** — small standalone script (plan item B1 from the Notion-research backlog), added 2026-09-10. Re-runs the same live Greenhouse/Lever API check `collectors/company_careers.py` uses against `REJECTED_CANDIDATES`, a short hardcoded list of boards previously confirmed to exist but have zero open jobs (currently Kraken, Prodly — see the "checked 2026-09-05"/"checked 2026-09-09" comments in `config/companies.yaml`). Reports whether any now have postings, so a board starting to hire doesn't require re-mining the whole source list by hand — does not touch `career_boards` itself, adding a newly-active board is still a manual decision (relevance check first).

**`scripts/mine_notion_companies.py`** — standalone Playwright script (plan item B2 from the Notion-research backlog), added 2026-09-10. Extracts every row of a Notion-embed table view (e.g. `https://agilefluent.notion.site/600-...`, the 599-company "Russian-speaking roots" directory mined earlier for `career_boards` candidates) into a CSV, by clicking "Load more" in a loop and re-querying the button fresh from the live DOM before every click — this is what the earlier interactive-browser-tool attempt couldn't do reliably (its cached element `ref` kept resolving to a stale screen position once the DOM grew). Row/column extraction (`.notion-table-view-row` / `[data-col-index]` / `.notion-table-view-header-cell` selectors) is generic to any Notion-embed table, not tied to this one page. Pagination/extraction logic itself is covered by tests (`tests/test_mine_notion_companies.py`, including a real-headless-browser integration test against a synthetic Notion-like DOM) and is confirmed correct.
**Known issue, confirmed harder than expected: `agilefluent.notion.site` is Cloudflare-protected and rate-limits automated page loads (HTTP 429) more aggressively than a normal retry-with-backoff can work around.** Across two separate sessions and roughly a dozen total load attempts (script runs plus earlier interactive-browser-tool use against the same URL), only a couple got past the block, and once actually past it the table view itself sometimes still rendered "No results" for several seconds before the client-side app finished hydrating — so a bare `wait_for_selector` on `.notion-table-view-row` isn't sufficient evidence of a block either way. **`core/cv_review.py`** (driven by `scripts/cv_review.py`) — plan item 8.3, added 2026-09-14: reviews an already-written draft (`CV/drafts/<job_id>.md`, exactly as it is on disk, hand edits included) via one Anthropic API call — a genuinely separate, stateless call from the one that drafted it, not the same context "checking its own work". **`core/pdf_assembly.py`** (driven by `scripts/cv_pdf.py`) — plan item 8.4, added 2026-09-14: assembles a one-page cover-note PDF per draft (title/company header, the pitch, the CV bullets) via Playwright `page.pdf()` — no new rendering dependency, Playwright was already required for the collectors. **No LLM call and no `ANTHROPIC_API_KEY` needed** — 8.4 is purely mechanical, unlike 8.1-8.3: `extract_draft_content` re-parses the pitch/bullets straight out of the (possibly hand-edited) draft markdown via regex, and the ATS keyword check reuses `record.required_skills`/`preferred_skills` (the rule-based analyzer's own output) rather than asking a model to name keywords again. `pypdf` (new, lightweight, pure-Python dependency) reads the *rendered PDF's actual text layer* back out — deliberately not the source HTML/markdown — since the point of an "ATS check" is to catch the real, mundane failure mode where a PDF looks fine visually but its text layer is garbled/unselectable (bad font embedding, ligatures), which only shows up by reading the PDF itself. **Confirmed working on all 16 live drafts (2026-09-14), one interesting real-world finding, not a bug**: the naive keyword check counts a skill as "matched" even when the pitch is explicitly *disclaiming* it (e.g. "I don't have direct Tableau/Snowflake/Airflow experience" registers all three as "found" in the PDF text) — this is left as-is because it faithfully mirrors how many real basic ATS keyword parsers actually behave (they're well known for not understanding negation), not a defect in this script. Worth keeping in mind when writing future pitches: naming a missing tool to be transparent about a gap can register as a false keyword hit on a naive parser, exactly the tradeoff a human has to weigh, which this tool surfaces rather than hides.

**`core/applications.py`** (driven by `scripts/applications_tracker.py`) — plan item 8.5, added 2026-09-15: the actual gate the roadmap called for. **The user's daily workflow in the processed workbook (since 2026-09-30).** A plain-language Russian guide for the user lives in `WORKFLOW_RU.md` (private repo only; keep it in sync when this changes). Only three tabs are visible, in this order; `core/storage.py:arrange_workbook_tabs` (called by every script that writes the workbook) hides `jobs_master`/`skills_gap`/`skill_recommendations` and puts these first:

- **`load_manual_review` used to leak pandas' NaN-for-a-blank-cell as the literal string `"nan"`** (`core/storage.py`), found 2026-09-11 the first time a fresh `--source all` + `analyzer.py` run produced brand-new, never-reviewed `manual_review` rows and `scripts/fit_score.py --limit 5` reported `0` candidates instead of the 8 that were actually sitting there undecided. Root cause: `pd.read_excel` reads an untouched blank cell as float `nan`, and `str(nan)` is the literal text `"nan"` — truthy and non-empty. Two consumers broke silently on this: `compute_personal_fit` folded it into a `"nan — nan"` personal_fit for every not-yet-reviewed posting (visible in the sheet, easy to miss since a fully-calibrated dataset never has any blank rows to trigger it), and `scripts/fit_score.py`'s `select_candidates` treated `"nan"` as a real `decision` and silently skipped scoring every brand-new posting — the exact case the whole cost-control design was built for. Fixed: `load_manual_review` now normalizes every NaN float to `""` before returning. Regression test: `tests/test_storage_and_logging.py:test_load_manual_review_returns_empty_string_not_nan_for_blank_cells` (saves twice — the bug only shows up on the *second* save, once blank cells have round-tripped through disk).
